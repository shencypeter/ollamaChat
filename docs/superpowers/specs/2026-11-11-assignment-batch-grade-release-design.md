# 同一作業全班一次發布成績設計

狀態：批次發布範圍已確認；遲交扣分公式待確認

## 目的

同一份線上作業、測驗、PDF 個人作業、PDF 小組作業或手動評分項目，成績只能以該評量的全體應評學生為單位一次發布。個別學生評閱階段只儲存草稿，不可單獨讓學生看到成績。

## 已確認範圍

- 發布單位是一份評量，不是單一學生，也不是整門課的所有評量。
- 個人評量的應評名單為該課目前有效且帳號有效的學生。
- 小組評量的應評名單為該作業指定小組中的有效／繳交快照學生；同組可有個別調整分數。
- 未繳交者仍屬應評名單。關閉上傳時不直接自動給 0；批次發布前由系統列出並請教師確認是否將未繳交者記為 0 分。
- 全體應評學生的草稿分數皆非 `null`、都在滿分範圍內，且頁面沒有未儲存修改時，才可發布。

## 行為

1. 個別評閱頁只保留「儲存評分草稿」，移除單人「發布成績／發布回饋／確認並寫入正式成績簿」。
2. 評量頁顯示完成度，例如「已評分 12／14 人」，並將尚未評分者分成「未繳交」與「已繳交但未批改」。
3. 教師要求發布時，如仍有未繳交且未評分者，系統顯示姓名／學號並詢問「這些學生是否為未繳交，確認記為 0 分？」；教師確認後才整批建立 0 分草稿。登錄 0 分不建立假的繳交紀錄，也不宣稱學生已作答。
4. 已繳交但未批改者不能透過上述確認自動給 0，仍會阻擋發布並提示先完成批改。
5. 評量頁提供唯一的「發布全班成績」按鈕。補齊未繳交 0 分後仍有 `null` 時不得發布。
6. 發布 API 在交易內重新鎖定並核對評量、名單、繳交狀態及所有草稿分數，不能依賴前端判斷；確認未繳交 0 分與全班發布可以在同一交易完成。
7. 驗證通過後一次複製全部草稿分數至 `published_score`，同步既有作業／測驗公開狀態與成績簿；任一筆失敗即全部回滾。
8. 學生在交易提交前看不到任何本次新成績；提交後每位學生只能看到自己的分數及允許公開的回饋。
9. 發布後若教師修改任何草稿，已發布版本仍保留；再次發布時仍須全班資料完整，並以一筆新的全班發布稽核覆寫公開版本。

## 資料與相容性

- 沿用 `course_grade_scores.score` 作為每位學生的草稿分數、`published_score` 作為學生可見分數。
- PDF 現有 `report_submissions.score`、小組 `report_snapshot.override_score` 及測驗 `grades` 保留作為評閱細節；儲存草稿時同步到成績項目的草稿分數。
- 經教師確認為未繳交 0 分的學生只有評分項目草稿／公開分數，不建立 submission 或 submission revision。
- 既有已個別發布資料不回收、不隱藏；首次採用新流程時視為歷史公開版本，後續只能整批發布。
- 不改變課程總成績的獨立發布流程，但課程總成績只採各評量已批次發布的 `published_score`。

## API 與授權

- 新增每份評量的發布狀態（應評、已評、未評、可發布）。
- 新增評量層級的批次發布 API，僅教師及具評分權限的助教可使用；沿用課程封存與學生體驗禁寫規則。
- 既有單人發布參數與端點不再執行發布；後端回覆衝突並要求使用批次發布，避免舊前端或手工 API 繞過。
- 每次批次發布保留操作者、評量、名單數、發布時間及被覆寫人數的稽核紀錄。

## 介面

- 批次發布控制放在該作業的「作業評閱與給分」頂端／底端，不放在個別學生卡片內。
- 顯示「草稿已評分 n／總數 m」、「未繳交 k 人」、「已繳交待批改 j 人」及未完成姓名。
- 發布前先確認是否將列出的未繳交者記為 0，再二次確認會同時讓全體應評學生看到成績。
- 小組作業仍逐組編輯基礎分與個別調整，但只在所有組員都有最終草稿分後一次發布。

## 驗證

- 個人、群組、線上測驗、PDF 及手動項目皆測試完整／缺分情境。
- 測試未繳交者只有在教師確認後得 0，取消確認不寫入，且不會產生繳交紀錄。
- 測試已繳交但未批改者不能被未繳交確認誤設為 0。
- 測試前端停用與後端直接呼叫皆無法部分發布。
- 測試批次交易任一錯誤時 0 人發布、成功時全體同時發布。
- 測試學生 API 在發布前無法讀取草稿，發布後只讀取本人資料。

## 考量過的替代方案

- 只檢查已有繳交者：會漏掉未繳交學生，不符合「全班一次發布」。
- 關閉上傳時自動將未繳交者設為 0：省步驟但可能錯誤懲罰學生，因此改採發布前列名確認。
- 只隱藏個人發布按鈕：舊 API 仍可部分發布，因此不採用。
