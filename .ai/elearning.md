## 第一批實作：學習歷程與測驗教材時間門檻（2026-11-04）

使用者後續要求照規格實作，已新增本人跨課／學期學習歷程、課內成績／提交進度、待辦、分頁時間軸與篩選，來源涵蓋測驗、PDF、案例、線下成績及教材有效時間。只讀本人仍有有效學生資格的課程，正式／練習／草稿隔離，未公布成績遮蔽；不宣稱全校校務資料完整。

教材新增PDF／圖片／MP4／WebM閱讀器與伺服器有界計時；測驗可逐教材設最低有效秒數，全部達標並明確開始才回傳題目及允許寫入。017新增表，不回填舊時數。每10秒保存、超過25秒中斷不計、文件60秒互動時限／背景暫停、影片1x／快轉不計／重看可累積，單人多分頁／裝置不重複；本人練習分開。發布前同一教材既有有效時間可沿用，發布鎖定門檻，開始保存依據；原期限／權限仍生效。

完整單元進度、完課／證書、校務介接與歷史退選存取、影片完成比例／續播、新跨修課匯出與公告仍後續，AI功能未擴充。現行操作與量測限制見 [學習歷程規格](../docs/learning-history-spec.md) 第一批實作；下方「僅規格／尚未實作」為同日早先規劃脈絡，由本節取代其已完成部分。

## 新增需求：教材閱讀時間作為線上測驗門檻（2026-11-04，原規劃）

線上測驗可由教師／助教指定本課影片、講義及其他教材，設定最低累積有效閱讀／觀看時間；學生達標後才可開始測驗，未啟用則沿用原開放規則。學生可查看要求、累積與尚差時間；達標仍受原測驗期限與權限限制。單純開啟／下載不視為達標，需伺服器驗證個人有效活動紀錄並排除背景、閒置與重疊計時。功能依賴教材追蹤，尚未實作，未自動納入 11/15 交付承諾；多教材組合、版本與既有時間沿用等設計見 [學習歷程規格](../docs/learning-history-spec.md)「線上測驗的教材閱讀／觀看時間門檻」。

## 最新規劃：本校學生跨修課學習歷程（2026-11-04，僅規格）

使用者要求將本校學生所有修課的學習歷程納入範圍：修課、學習進度、學習時間、影片觀看、教材閱讀、測驗、作業、完課、學習證明、查詢及報表匯出。跨課程／跨學期以學生本人為中心，現有 T2 單課案例歷程只是其中一個資料來源；跨課彙整不改變課程獨立與禁止跨課共用教材的政策。

11/15 建議候選為平台內本人修課總覽、正式提交與可見成績時間軸、評量提交進度、站內截止待辦及基本成效儀表板；CSV 視餘裕加入。全校完整修課需校務資料與可靠身分對應，完整單元進度、有效活動時間、影片續播、完課規則、證書與校級授權另階段實作。下載不等於已讀、停留不等於有效學習時數、提交完成不等於完課，平台成績不冒充正式學分／GPA。

本次只有規劃與可行性評估，未執行產品開發／部署；候選優先級非教授核定。後期 AI 助教、AI 推薦／出題不優先納入 11/15，既有客觀題規則批改可展示。完整範圍、其他 LMS 亮點取捨、估算、權限、保存及驗收見 [學習歷程規格與 11/15 評估](../docs/learning-history-spec.md)。舊 P0／P1 交付紀錄保留，新增候選不視為已完成或固定承諾。

## 最新決策：平台管理權限與課程角色分離（2026-11-03，已實作）

使用者採用兩層設計：平台管理權限為「管理員／一般成員」，「可建立課程」為管理員可授予／撤銷的獨立資格，不自動隨管理員或課程教師身分取得。課程角色才區分「授課教師／助教／學生」，同一帳號可在不同課程擔任不同角色；一般成員可由課程擁有者安排任一課程角色，不再以全域教授／助教／學生限制搭配。

有建課資格者建立課程後成為擁有者及授課教師。擁有者管理本課成員，教師／助教依課程角色管理教學內容；平台管理員不自動取得其他課程的資源、私密答案或學生紀錄。學生體驗與首頁／資料填寫依各課情境判定，正式與練習隔離沿用。此決策取代舊「所有教授兼任管理者」及全域角色搭配限制的現行規格，保留舊實作紀錄。

已依後續使用者指示實作，015 遷移原平台角色為管理員／一般成員及獨立建課資格；原課程角色保持。舊 session 需重新登入。完整授權矩陣、管理頁拆分、遷移與驗收見 [角色與權限規格](../docs/role-permissions-spec.md)。

## 最新決策：取消班別，只保留課程（2026-11-03，已實作）

使用者指定一門課程代表一個實際授課群體；課程下直接管理學員、小組、資源、測驗、PDF 作業、案例與成績，不再設班級／班別。學員只需加入課程，小組只接受本課有效學生，每人每課至多一個有效小組，組名在課內唯一。資源以課程授權，移除班別範圍；每個課程獨立，不提供跨課程資源共用、分享或共用檔案庫。同一份教材用於不同課程時，需於各課程分別上傳，各有獨立資源紀錄、版本與下載次數；更新或刪除不影響其他課程。

本決策取代下方第十七、二十、二十一節及其他班別／調班／限班資源描述的現行需求效力；這些段落僅保留原分班實作歷史；新規格已依後續指示部署。取消班別不影響其他後續需求，例如客觀題自動批改、練習提交、文件名稱與預覽。

已按使用者選擇，將一三五／二四六轉為獨立課程並複製各自評量與資源；未分班學生留一三五，原小組／紀錄保留。已盤點無限定資源或提交衝突，016 退役班別。完整目標、檔案清單、遷移與驗收見 [單一課程層級規格](../docs/course-only-spec.md)。

## 一、目標與交付原則

建立具有使用者帳號、課程、個人作業與作答流程的線上學習平台，並將既有 LLM 教學助教保留為獨立的 AI 入口。介面採類似 Teams 的工作區配置，支援淺色與深色主題。

POC 的用途是讓教授與學生操作具體流程，據此討論教學方式、評閱標準與後續需求。可執行的功能不代表教學設計或 AI 評分已獲驗證。

- **P0：11/15 展示必須具備。** 帳號與登入、角色權限、課程建立、課程名單、個人作業與作答。
- **P1：11/15 展示加入人工教學評閱流程，12/31 第一階段交付。** AI 教學助教整合另排 12/15；不屬本次 P1 實作。
- **P2：2027 年第二階段擴充。** 先規劃，不納入目前實作承諾。

P0 主要流程已完成；使用者於 2026-10-27 授權加入 P1 人工教學評閱流程，取代原先只修正 P0 缺陷的凍結安排。11/15 展示包含本次 P1，12/15 預定 AI 整合，12/31 第一階段交付。上述分級是團隊初步規劃，尚非主管與教授核定的完整需求清單。

## 二、角色與權限

平台角色與課程角色分開管理。是否能操作某門課程，以該課程的有效成員身分為準；平台教授不會自動取得所有課程的內容存取權。

| 層級 | 角色 | 主要權限 |
| --- | --- | --- |
| 平台 | 教授 `Professor` | 建立帳號與課程；管理自己擁有課程的成員與角色 |
| 平台 | 助教 `TeachingAssistant` | 登入平台、使用所屬課程及 AI 入口 |
| 平台 | 學生 `Student` | 登入平台、使用所屬課程及 AI 入口 |
| 課程 | 教師 `teacher` | 建立、編輯、發布、關閉個人作業；檢視已提交作答 |
| 課程 | 助教 `ta` | 建立、編輯、發布、關閉個人作業；檢視已提交作答 |
| 課程 | 學生 `student` | 閱讀已發布作業、儲存自己的草稿、提交及查看自己的作答 |

學生不得列舉平台帳號、查看其他學生作答，或透過指定使用者識別碼冒用他人身分。教師與助教的作業檢閱介面只提供已提交內容，不提供學生未提交草稿。

## 教師／助教學生體驗（2026-10-29）

教授與助教可從頁首切換「學生視角」，操作本人練習草稿；提交按鈕可見但不可使用，正式提交仍須由學生本人操作；不冒用學生，不更改帳號角色或課程成員。伺服器驗證模式資格與有效課程成員，學生視角只看已發布作業，沿用時間與提交政策。

練習以 submissions.is_practice 隔離，正式名單、提交計數、人工評分及發布入口排除練習。私人 AI 回饋、快照及一般對話記憶均依本人與模式隔離；學生體驗不提供教授原始請求／回應檢視。切回教學視角恢復原功能，舊資料不刪除。

005 遷移已套用；偏好依登入帳號儲存於本機，並非新角色授權。完整矩陣、API 邊界、限制與測試見 [學生體驗模式](../docs/student-experience.md)。示範作業仍為未發布草稿，需教授自行發布後才能以學生視角操作。

## 三、帳號與登入

- 空白帳號資料庫以初始化代碼建立第一位教授；第一個帳號建立後即關閉初始化入口。
- 教授建立後續教授、助教及學生帳號。沒有自動建立的示範密碼或任意切換角色入口。
- 密碼至少 12 字元，以雜湊儲存；登入失敗具鎖定及請求頻率限制。
- 使用 Cookie 驗證，Cookie 為 HttpOnly；非開發環境要求 HTTPS。修改密碼後登出目前工作階段。
- API 寫入操作需要防偽權杖；未登入及權限不足分別回傳 401、403。
- 問候、頁首與頭像顯示中文名字時，移除第一個姓氏字元；完整姓名仍保留於帳號、名單與提交紀錄。複姓辨識尚未實作。

初始化代碼、資料庫密碼及連線憑證不得寫入本規格或前端程式碼。

## 四、課程與名單

- 教授建立課程，包含課程代碼、名稱與學期，並成為課程擁有者及教師成員。
- 課程代碼與學期組合不可重複。
- 使用者的「我的課程」列出其有效成員課程。
- 課程擁有教授管理成員及課程角色；教師與助教可讀取課程名單。
- 課程資料模型支援草稿、啟用及封存狀態；封存課程禁止作業寫入。完整課程生命週期管理介面不視為已交付。

## 五、P0 個人作業流程

主要流程：**教師／助教建立草稿 → 編輯並發布 → 學生儲存與重新載入草稿 → 學生提交 → 教師／助教檢閱提交內容與版本。**

### 5.1 作業建立與發布

- 作業包含標題、選填的說明或案例、選填的開放與截止時間，以及 1–20 題申論、是非、單選或多選題目。
- 題目可選擇對應四個分析階段之一；「加入四階段題目」只是新增可編輯題目，不會觸發 AI。
- 草稿可編輯，學生無法讀取未發布草稿。
- 發布後鎖定題目、說明及日期；教師／助教可關閉已發布作業。
- 狀態轉換為 `draft → published → closed`。P0 不提供重新開放、撤回發布或發布後修改題目。

### 5.2 學生作答與提交

- 每位學生每份作業保留一份提交容器（`attempt_no=1`）；P0 預設一次提交，P1 可明確允許期限內產生多份不可覆寫的正式提交快照。
- 每題最多 16,000 字元；草稿可留白，正式提交必須完成所有題目。
- 草稿以明確的儲存操作寫入 PostgreSQL，重新載入後可繼續作答；目前不宣稱具備自動儲存。
- 已變更的答案新增版本，未變更答案不重複建立版本。
- 提交時原子性更新提交狀態、伺服器時間及目前答案版本的提交標記。
- 預設提交後唯讀，不提供撤回或教師代改；P1 開啟修訂政策時可直接提交新版本，保留舊快照與各版本成績。
- 離開或重新整理前，對未儲存修改提出提醒。

### 5.3 時間與資料一致性

- 以伺服器時間判定；開放時間包含該時點，截止時間不包含該時點。
- 開放前、截止時刻起、作業關閉後或課程封存後，禁止儲存及提交。
- 日期以 UTC 儲存，依裝置本地時區顯示。
- 截止或關閉後仍可閱讀自己已儲存及提交的內容；畫面上的未儲存文字保留為可選取內容，便於複製。
- 學生儲存使用版本檢查，教師編輯使用編輯版本檢查；過期頁面或同時寫入衝突回傳 409，不直接覆蓋。
- 拒絕跨作業題目、重複題目、缺漏題目及不完整提交；失敗時回復整筆交易。
- 使用交易與作業資料列鎖定，協調作業狀態變更與學生儲存。

### 5.4 教師與助教檢閱

- 列出已提交學生、完整姓名及伺服器提交時間。
- 閱讀各題提交內容與已儲存的修改歷程。
- 不提供未提交草稿的檢閱入口。
- P1 已加入人工評分草稿、明確發布與變更歷程；作業 AI 評分與私人形成性回饋依 2026-10-29 新需求停用；保留獨立 AI 入口。

## P1：人工評閱與教學流程（2026-10-27 新增）

- 作業草稿可設定滿分、同課程規準及是否允許提交後修訂；發布後鎖定。
- 每次提交有整份答案快照、作者、提交序號與時間；學生與課程教師／助教可比較兩版。
- 人工成績綁定指定快照，保留評閱者、時間、分項、回饋與修改歷程；新提交不繼承舊分數。
- 評分先儲存草稿，再由教師／助教發布。學生只可讀自己的已發布成績，舊發布紀錄保留。
- 規準有項目、說明、四個等級與權重；加權級別除以滿級後換算作業滿分。各項 1 級為滿分四分之一，各項 4 級為滿分。
- 規準已關聯作業後，編輯會建立新版本，不改變既有關聯與評閱；同課程可重用。
- 新增 SQL 遷移 `003_teaching_workflows.sql`，沿用既有 Npgsql 交易與遷移工具，不導入平行 EF Core 歷史。
- 完整政策、API、示範及實際驗證見 [P1 交付文件](../docs/p1-teaching.md)。AI 整合仍不在此次實作範圍。

## 作業 AI 暫停政策（2026-10-29，取代 10/28 形成性政策）

依使用者確認，作業頁全部停用 AI：不載入／請求私人回饋、不顯示 AI 分數、提交不再詢問 AI 回饋。既有形成性 GET／POST API 回傳 403；舊紀錄保留，不刪除。教師／助教的學生體驗亦同。獨立 AI 入口維持原功能與模型設定。先前功能與測試保留於歷史文件，不代表目前開放。

## 六、AI 教學入口

### 6.1 使用範圍

既有 LLM 表單已移至 Vue 的獨立 AI 入口，保留單份評閱、修改前後比較及一般對話。四個評閱階段為：

1. 病前功能。
2. 疾病病程。
3. 功能評估結果。
4. 心理社會條件。

評閱只使用目前請求所提供的作答與選填案例，不引用其他階段或舊回饋。比較模式分別評估修改前後版本，顯示兩份分數；品質相近可以同分，退步可以降分。

對話狀態依登入帳號及階段隔離。保留既有四種記憶策略、模型連線檢查與請求遙測。一般對話 Markdown 經清理；評閱欄位以文字呈現。

AI 入口目前不會建立正式作業提交、答案版本、資料庫評閱紀錄或正式成績。重新啟動服務會清除程序內的 AI 對話狀態。

### 6.2 四級評分規準

| 分數 | 定義與判定邊界 |
| --- | --- |
| 4 | 分析完整，準確引用案例證據支持論點，臨床推理適切；完整性、證據及推理須同時符合最高級別 |
| 3 | 分析大致正確，有少量遺漏或部分證據不足；問題限於不改變核心分析的細節 |
| 2 | 僅完成部分分析，有重大遺漏或缺乏支持的核心結論；仍有部分相關分析 |
| 1 | 分析不足、有重大誤解，或幾乎未提供相關依據 |

評閱需檢查相關事實、各主張的證據充分性、重要遺漏、臨床推理及無支持或矛盾的結論。文字流暢或語氣自信不能替代證據。影響核心分析的無支持推論必須實質影響分數；不得以關鍵字或錯誤數量機械計分。

### 6.3 結構化發現與驗證

模型在一次推論請求中，先輸出精簡且可核查的發現，再輸出分數及理由；不要求或呈現私人思考鏈。

每份評閱包含：

- `version`：本次、修改前或修改後版本。
- `caseEvidenceAvailable`：是否提供原始案例。
- `supportedClaims`：有據支持的主張。
- `partiallySupportedClaims`：僅部分支持的主張。
- `unsupportedClaims`：無支持、矛盾或推論不成立的主張。
- `unverifiedClaims`：無法從本次案例核實的事實轉述。
- `importantOmissions`：案例已提供但學生遺漏的重要資訊。
- `reasoningQuality`：精簡推理品質評述。
- `score`：1–4 的整數。
- `justification`：連結發現與級別的理由。

每項發現具有 `claim`、`evidence`、`explanation`。最外層為 `evaluations` 與 `comparisonFeedback`；單份評閱的比較欄位必須為空字串。

未提供案例時，必須明確標示無法核實準確性與完整性、分數為暫定。此時有據支持、部分支持與重要遺漏陣列必須為空；事實轉述列為未核實，仍可指出作答本身的矛盾或不成立推論。不得假裝已查核原始案例，也不得憑空扣除案例遺漏分數。

透過 Ollama JSON Schema 約束輸出，後端另驗證必要欄位、型別、分數、版本、案例旗標及解析失敗。格式正確不代表臨床內容或評分正確；不以硬編碼答案或分數補足模型判斷。

### 6.5 評估與診斷要求

### 教授／助教的唯讀請求檢視（2026-10-27）

AI 入口提供「系統詞與實際請求（唯讀）」展開區。教授與助教可在送出評閱、比較或一般對話後，查看自己該次操作實際組裝的 system 訊息、案例／答案／對話脈絡、指定模型參數、完整 JSON／Schema，以及每筆請求對應的 HTTP 狀態碼與 Ollama 原始 JSON 回應。若有記憶摘要推論，按送出順序另列；評閱結果無法解析時仍可檢視模型實際回傳的 JSON。

權限由後端登入角色檢查；學生的成功與錯誤回應均不包含請求檢視欄位，沒有跨使用者或全站歷史查詢入口。資料只存在本次 HTTP 操作與目前頁面記憶體，不加入資料庫、日誌、對話歷史或瀏覽器持久儲存，重新載入後清除。請求與回應中的模型 `thinking` 欄位會由後端遞迴移除，端點亦移除憑證與查詢字串；若回應不是可安全解析的 JSON，不將未清理的原始文字送到前端。

此功能是為教授討論「是否自行調整系統詞」提供具體依據，目前不提供編輯、套用或回復指令；也不代表已取得 Ollama 內部套用模板後的最終 token。舊的開發專用去識別診斷仍獨立且預設停用。

### 評估原則（續）

- 測試作答及預期分數與正式提示分離；預期級別須視為待合格評閱者確認的暫定標記。
- 評估弱強區辨、無支持結論的影響、重複評閱一致性、改寫一致性，以及回饋與分數是否相符。
- 記錄模型識別、抽樣參數、提示版本、作答、結構化發現與分數。
- 程式正確性測試與人工評分一致性分開報告，不將 JSON 成功率視為評分準確率。
- 完整組裝請求的診斷僅在開發環境明確啟用，於程序記憶體保留去識別副本；不提供公開 HTTP 入口，正式環境預設停用。

## 十三、課程功能結構與線下評分（2026-10-29）

依使用者最新要求，課程內提供五個功能入口：

1. **教學資源／講義**：檔案上傳、下載與下載次數。

4. **考試管理 → 個別考試 → 排行榜**：題目／評閱與排行榜分入口，排行榜依名次或學號排序；完整榜單仍只給教師／助教。
